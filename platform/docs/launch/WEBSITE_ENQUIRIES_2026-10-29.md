# CCS website contact-mail replacement — 29 October 2026

FormSubmit returns HTTP 521 from the checked environments and the authorised internal website test did not yield a receipt. Replace that dependency with the already configured business Resend transport. No new account, key, domain, plan or payment is created.

The isolated /api/quenvira/website-enquiry route receives only requests with one of the three recognised CCS website origins. It handles CORS preflight and validated JSON, has a body-size limit, validates all fields, ignores client-supplied recipients/senders, and sends plain text only. Recipient is fixed to ccscreativetech@gmail.com, sender to the existing verified domain. CCS_WEBSITE_ENQUIRIES=yes is a separate non-secret enable flag; existing email-test allowlist must already include the owner inbox. This does not enable customer invoice email, paid billing or self-service.

There are no D1 migrations or changes to workspace/invoice/customer records. Existing R2 storage uses a separate ccs-contact/ prefix only for hashed request metadata, acceptance state, provider ID and quota counters. Raw enquiry text, email, name and IP are not stored there. Salted-by-day IP hashes support a two-per-client/day limit; a conditional-write quota caps all website contact messages to five/day, preserving headroom alongside the existing invoice-attempt cap. No automatic retries. A duplicate accepted reference returns acceptance without sending again. A pending/uncertain prior reference is held for manual reconciliation; payload changes under an existing reference are rejected. Metadata older than seven days is removed on subsequent contact requests. No storage residency promise is inferred.

Email keys remain in the existing server environment and are never returned or copied to the browser. Contact messages carry a source=ccs-enquiry provider tag. Signed callbacks for this tag are acknowledged separately without touching invoice delivery rows; signature checking still precedes tag handling.
